## 一、使用者裁決（2026-08-10）

| 決策點 | 結論 |

## 二、現況盤點

- `設備技術資料\設備維護一覽表.xlsx` 形同空白：`總表` 只有 2 台（M01-101 機械手臂半年換電池、
  D01-101 一年），`維護記錄` 只有 3 筆。**等於全新開始**，但這 5 筆要一次性匯入不要丟。
  該檔欄位（設備名稱／設備編號／維護週期／維護內容／注意事項／附件）已被下面的 schema 完全涵蓋。
- 已可直接沿用的底座：設備主檔 189 台／41 種類型（`equipment.db`）、行事曆
  `_cal_workdays()`（`docs/calendar.md`）、異動歷程 `eq_history`、`static/vendor/JsBarcode`、
  設備詳情抽屜、左側選單版面。
- **不能沿用的**：維修記錄那條線（資料來源是唯讀的 Google 採購登入表，寫不回去），
  所以保養執行結果一律存在自己的資料表，不要嘗試回寫採購表。

## 三、資料模型（新增在 `equipment.db`，網芳共用）

### 3.1 基準書與項目

```sql
-- 一份基準書 = 一種機台類型的保養標準（或某台設備的專屬版本）
mt_standard (
  id INTEGER PRIMARY KEY,
  scope      TEXT,     -- 'type'（類型範本）| 'equip'（單機專屬加項）
  group_code TEXT,     -- scope='type' 用：A / B / C…
  type_code  TEXT,     -- scope='type' 用：03 / 04…
  code       TEXT,     -- scope='equip' 用：A03-501
  title      TEXT,     -- A03 立式綜合加工機 保養基準書
  rev        TEXT,     -- 版次 A/B/C
  rev_date   TEXT,
  author     TEXT,
  status     TEXT,     -- 草稿 / 生效 / 停用
  note       TEXT,
  created_at, updated_at
)

-- 基準書明細列 = 一個保養項目
mt_item (
  id INTEGER PRIMARY KEY,
  std_id     INTEGER,  -- 屬於哪份基準書
  seq        INTEGER,  -- 項次（排序）
  part       TEXT,     -- 部位：主軸／導軌／潤滑／氣壓／電氣／冷卻／外觀
  name       TEXT,     -- 保養內容：導軌潤滑油量確認
  method     TEXT,     -- 方法：目視／清潔／加油／更換／量測／校正
  criteria   TEXT,     -- 判定基準：油位在上下限之間（這欄是「基準書」跟「待辦清單」的分水嶺，必填）
  cycle_kind TEXT,     -- day / week / month / quarter / half / year
  cycle_n    INTEGER,  -- 每 N 個單位（每季 = quarter,1；每 3 個月 = month,3）
  anchor     TEXT,     -- 起算基準日 YYYY-MM-DD（空=用設備採購日，再空=用啟用日）
  duration_min INTEGER,-- 標準工時（分）
  need_stop  INTEGER,  -- 是否需停機（排程時要避開生產）
  owner      TEXT,     -- 操作員 / 保養員 / 委外廠商
  tools      TEXT,     -- 工具與耗材：六角板手、油槍、濾網
  oil_code   TEXT,     -- 使用油品：油品主檔 oil.db 的代號（優先，2026-08-11 加）
  oil        TEXT,     -- 使用油品：主檔沒有這支時的自行輸入文字
  safety     TEXT,     -- 安全注意事項（對應舊 Excel 的「注意事項」）
  attach     TEXT,     -- 附件檔名（對應舊 Excel 的「附件」，實體放網芳）
  active     INTEGER,
  created_at, updated_at
)
```

### 3.2 單機覆寫（**差異表，不是複製整份**）

```sql
mt_equip_item (
  code    TEXT,        -- 設備編碼
  item_id INTEGER,     -- 範本項目
  disabled INTEGER,    -- 1 = 這台不做這項
  cycle_kind TEXT,     -- NULL = 沿用範本
  cycle_n    INTEGER,  -- NULL = 沿用範本
  anchor     TEXT,     -- NULL = 沿用範本
  note    TEXT,
  PRIMARY KEY(code, item_id)
)
```

**為什麼用差異表而不是把範本複製給每台**：範本改一個字要同步 189 台是災難，而且會分不清
「這台真的不同」還是「忘了同步」。單機真正獨有的項目走 `scope='equip'` 的基準書收納，
兩種需求各有明確去處。

### 3.3 展開後的保養工作

```sql
mt_plan (
  id INTEGER PRIMARY KEY,
  code       TEXT,     -- 設備編碼
  item_id    INTEGER,  -- 來源項目
  due_date   TEXT,     -- 應執行日 YYYY-MM-DD
  period_key TEXT,     -- 2026 / 2026-H1 / 2026-Q3 / 2026-08 / 2026-W32 / 2026-08-10
  status     TEXT,     -- 待辦 / 已完成 / 跳過 / 免做
  done_date  TEXT, done_by TEXT,
  result     TEXT,     -- OK / NG
  minutes    REAL,     -- 實際工時
  remark     TEXT,
  photo      TEXT,     -- 回報照片檔名（實體在網芳）
  created_at, updated_at,
  UNIQUE(code, item_id, period_key)
)
```

**`UNIQUE(code, item_id, period_key)` 是整個展開機制的關鍵**：展開作業可以重複執行任意次
（每次開頁面就跑、手動按鈕跑、每月跑），只會補上缺的，不會產生重複待辦。不要拿 `due_date`
當唯一鍵——調整週期時 `due_date` 會變，`period_key` 不會。

### 3.4 到期日規則（固定錨點，不順延）

```
due_date = anchor 起算，每 cycle_n 個 cycle_kind 一次，落點若非工作日 → 用行事曆往後推到最近工作日
```

**做完的日期不影響下一期到期日**（固定錨點）。晚做只會讓該筆標「逾期完成」，
不會把整條時間軸往後推——年度計畫甘特表要能事先畫出來、稽核要能對照，浮動週期做不到這件事。
日後若某類設備真的需要「從上次完成起算」，在 `mt_item` 加一個 `float_cycle` 旗標即可，
不要改動預設行為。

### 3.5 日／週點檢不預先展開（重要）

189 台 × 日常點檢 10 項 × 365 天 ≈ 69 萬筆空待辦，會把網芳上的 SQLite 拖垮。做法：

| 週期 | 展開時機 |
|---|---|
| 月／季／半年／年 | **預先展開**（可展開未來 12 個月），進排程清單與甘特表 |
| 日／週 | **不預先展開**，現場掃碼開啟當日點檢表時才 lazy INSERT（`period_key` = 當天日期／週次） |

因此「今日應點檢項目」是即時算出來的，不是查表查出來的；`mt_plan` 裡只會留下**真的做過**
的日／週點檢記錄。

## 四、與既有功能的接點

| 既有功能 | 接法 |
|---|---|
| `eq_history` 異動歷程 | 保養完成寫一筆 `action='保養'`。**只寫月以上週期與 NG 異常**，日／週點檢不寫——每天 189 筆會把移轉／狀態變更這些真正重要的歷程洗掉（同 `_EQ_TRACKED_FIELDS` 刻意不追蹤備註的理由） |
| 行事曆 `_cal_workdays()` | 到期日避開非工作日；「本月應完成 N 項」的統計一律呼叫它，不要自己寫 `weekday()<5` |
| 妥善率 | 保養停機時數可選擇是否計入停機（建議**預設不計入**：計畫保養不是故障，混在一起會讓妥善率失去意義；要看就另外出「計畫停機」欄位） |
| 維修記錄（Google 採購表） | 單向：NG 項目可標記「已開維修」，但**不回寫採購表**。日後若要關聯，用 `rep_key` 對應 |
| 設備詳情抽屜 | 新增「🔧 保養」區塊：適用基準書、各項下次到期日、最近 N 筆保養記錄 |
| `status` 狀態 | 只對 `使用中`／`閒置` 展開；報廢／已售出／轉賣不展開（同妥善率的處理原則） |

設備管理頁（`/equipment_master`）左側選單新增第三組 **📁 保養管理**：

## 六、手機掃碼回報

1. **條碼內容 = PDM 編碼**（`A03-501`）。現有 `JsBarcode` 是一維碼，手機掃一維碼體驗差，
   建議改用 QR；**依硬規則必須把 QR 函式庫下載到 `static/vendor/`**，禁止 CDN。
2. 設備標籤列印頁：編碼 + QR + 設備名稱，貼在機台上。
3. 手機版路由 `/m/eq/<code>`：單欄大按鈕版面，顯示設備照片、今日/逾期保養項目、
   一鍵「完成／NG」、拍照上傳、備註。**不做完整設備管理功能**，只做回報。
4. **前置條件（要先確認，會卡住整個 P3）**：
   - 手機要連得到 Flask 的 5088 埠 → 伺服器所在電腦的 Windows 防火牆要開放內網、
     手機要在公司 Wi-Fi。
   - 目前系統是「桌面 --app 模式跑在使用者自己的電腦」，那台關機手機就進不來。
     手機回報要能用，**得先決定一台常開的機器當服務端**（或直接跑在 192.168.1.99 那類常開主機）。
   - 現場是否有足夠的公司 Wi-Fi 覆蓋、作業人員是否用自己的手機。

## 七、寫入頻率與網芳鎖檔

`equipment.db` 在 Windows 網芳上（見 `docs/equipment-master.md` 十一節），保養回報會明顯
增加寫入次數。原則：

- 每次回報只做**一筆短 UPDATE**，不要在同一個交易裡做大量寫入。
- 回報照片實體存網芳資料夾，DB 只存檔名（跟設備照片同做法）。
- 展開作業（可能一次 INSERT 上千筆）**不要在使用者開頁面時同步跑**：改成手動按鈕
  或每天一次，並分批 commit。
- 沿用 `_eq_conn()` 的 `timeout=15`，**不要**因為這個功能就去開 WAL（網芳上更不穩）。

## 九、落地關鍵：基準書內容誰來寫

技術做完不等於能用——**41 種類型 × 10~20 項 ≈ 400~800 列的內容要人寫**，這是本功能最大的
實際成本。建議：

- 先做涵蓋率最高的三群：**A 群組 CNC 43 台、B 鑽床 49 台、C 沖床 30 台 = 122 台（65%）**，
  其餘類型可以先掛空基準書慢慢補。
- 系統一定要提供「**複製自其他類型**」（A03 複製到 A05 再改幾行）與 **Excel 匯入/匯出**，
  讓人可以在 Excel 上大量編輯再貼回來——沒有這兩個功能，內容永遠建不完。
- 內容來源優先序：原廠保養手冊（`設備技術資料\` 底下已有 23 個資料夾）→ 現場師傅經驗
  → 過去維修記錄（哪些項目常壞就該被納入保養）。

### 使用油品：參照油品主檔（`oil_code` → `oil.db`）

跟「工具與耗材」分開存：油品是**現場單獨會被問、之後也要拿來統計用量與叫料**的東西
（「這台要用哪些油」「全廠共用幾種油」），混在耗材那串文字裡就撈不出來。表格上有自己
一欄、抽屜也顯示，用橘色 `.mt-oil` 徽章標記。

**選單來自油品管理的油品主檔**（`GET /api/equipment_master/maint/oil_options` 讀
`oil.db`，見 `docs/oil-management.md`），依分類分組。

**停用的油品不列在下拉裡**（已經不能領用，選了也沒意義）——但**這個項目現在就選著的那支
停用油品是例外**，仍會留在清單裡並標「（停用）」：不留著的話一存檔就被默默清掉，
使用者根本不知道自己剛剛弄丟了一筆資料。端點本身回傳全部（含停用），過濾是在前端做的，
因為要判斷「是不是目前選著的那支」。

**選項與徽章都只顯示代號**：代號本身已經帶中文說明（`「半合成切削液」AW-30`），
再接上完整品名（`STORK金屬加工液 SW5031-030`）會把下拉與表格欄位撐爆；
完整品名放 `title`，滑鼠移過去看。

| 情況 | 存法 | 顯示 |
|---|---|---|
| 選了主檔油品 | `oil_code=代號`、`oil` 留空 | 代號，徽章可點 → `/oil?code=…` 開該支詳情看 MSDS |
| 主檔沒有這支 | 下拉選「── 主檔沒有，自行輸入 ──」，文字存 `oil` | 純文字徽章，不可點 |
| 代號在主檔查不到 | `oil_code` 還在，`oil_missing=True` | **紅底**徽章 +「（主檔查無）」 |
| 主檔裡是停用 | 同上但 `oil_status='停用'` | **紅底**徽章 +「（已停用）」 |

**顯示名稱一律以主檔當下的值為準，不存快照**（`_mt_fill_oil()`）：油品在主檔改了品名或
改成停用，基準書上要立刻看得到，不然現場照著一份寫著已停用油品的基準書去領料。
匯出 Excel 的油品欄也走同一條路。

`oil.db` 跟 `equipment.db` 是**兩個不同的資料庫檔案，join 不了**，所以在 Python 這邊補：
一次把用到的代號查完再配回去，不要每筆各開一次連線（都在網芳上，來回很貴）。
油品主檔還沒建立時 `_oil_conn()` 回 None，下拉就是空的，不影響基準書其他功能。

`/maint/tree` 另外回傳 `oils` / `parts`（跨全部基準書的相異值）給「自行輸入」與部位欄位
當 `<datalist>` 候選。

`/oil` 支援 `?code=` 深連結（頁尾 `_deepCode`），就是給這個徽章用的。

**加欄位一定要走 `_MT_ADDED_COLUMNS` + `_mt_ensure_columns()`**：`mt_item` 是執行期資料表，
正式機那份早就建好了，`CREATE TABLE IF NOT EXISTS` 對已存在的表**不會**補欄位——只改上面的
CREATE 語句對現有資料庫完全沒作用（同 `equipment.db` 加 `model` 欄位踩過的坑，見
`docs/equipment-master.md`）。日後再加欄位就往 `_MT_ADDED_COLUMNS` 加一行，其餘不用動。
實測：用還沒有 `oil` 欄的舊資料庫開一次連線就自動補上，既有 3 筆項目資料完好、新欄位為 NULL。

### 附件（PDF 保養手冊／注意事項）

實體檔案放網芳 `config.EQUIPMENT_MAINT_ROOT`（`D.設備\保養基準書\`）底下，**資料夾用看得懂的
名字**——類型範本是 `B01`、單台專屬是設備編碼 `M01-101`，理由同設備照片：沒裝系統的人直接開
資料夾也要知道那疊 PDF 是哪個機型的。資料庫只存檔名。

- **附件掛在「基準書」層、不是項目層**，所以項目還沒存檔就能先把檔案拖進去（上傳只需要 `std_id`）。
- `mt_item.attach` 存 `|` 分隔的檔名清單，一個項目可以掛多個檔。
- 撞名自動加時間戳記後綴，**不覆蓋**既有檔案（同照片上傳的做法）。
- 允許副檔名見 `_MT_ATTACH_EXT`（pdf／jpg/png…／doc(x)／xls(x)／txt），其餘該筆略過不中斷整批。
- 讀取一律走 `_eq_safe_path` 擋路徑跳脫（實測 `../../equipment_test.db` 兩種斜線都回 404）。
- **舊資料的 `attach` 只是一段文字說明**（例如舊維護一覽表的「240329 機械手臂電池更換注意事項」，
  沒有對應檔案）。`_mt_attach_list()` 會回 `exists=False`，前端顯示成灰色純文字而不是連結，
  免得點下去 404。
- 前端三種收檔方式：拖曳、點一下選檔、**Ctrl+V**（用瀏覽器原生 `paste` 事件，只在項目編輯
  表單開著且剪貼簿裡真的有檔案時攔截；表單關著時不攔，不會影響抽屜貼照片那條路徑）。
- 移除附件只是**把檔名從這個項目拿掉，實體檔案留在網芳資料夾**——共用資料夾上不做無聲刪檔。

### 端點

| 端點 | 說明 |
|---|---|
| `POST .../maint/plan/expand` | 展開待辦（`months` 預設 12，上限 24），**可重複執行** |
| `GET .../maint/plan/list?scope=` | 排程清單。`due`（預設：逾期＋未來 7 天）／`month&ym=`／`all`／`range&start=&end=` |

| `POST .../maint/plan/done` | 回報（`已完成`／`跳過`，判定 OK/NG、執行人、工時、備註） |
| `POST .../maint/plan/undo` | 退回待辦，連同自動寫的那筆 `eq_history` 一起刪 |

### 展開的四條規則（`maint_plan_expand`）

1. **只展開 `使用中`／`閒置` 的設備**，`停用` 的基準書整份跳過。
2. **視窗 = 今天往前 30 天 ~ 往後 N 個月**。**刻意不從採購日補完整歷史**——那會一次生出
   好幾萬筆從來沒人做過的「逾期」，清單直接不能看，而且過去根本沒發生的保養不該被記成漏做。
3. **重複執行安全**：`INSERT … ON CONFLICT(code,item_id,period_key) DO UPDATE … WHERE
   status='待辦'`。已存在的期別只修正**待辦**那些的 `due_date`（有人改了週期就跟著調整），
   已完成／跳過的一律不動。
4. **清掉不再適用的待辦**：項目被刪、被某台停用、設備報廢 → 該台該項的待辦整批刪除，
   不留殭屍任務（已完成的保留，那是歷史）。

到期日落在非工作日時往後推到最近的工作日（`_mt_shift_workday`，吃管理頁行事曆的設定，
最多推 14 天當保險絲）。

### 日／週不預先展開：清單上是「虛擬列」

`mt_plan` 只存月以上週期，以及**真的被回報過**的日／週點檢。清單裡 `id=null` 的是即時算出來的
虛擬列，回報時前端改帶 `code+item_id+period_key`，後端這時才 lazy 寫進資料庫。

**虛擬列的視窗要獨立算，而且分週期給不同區間**（2026-08-11 實測踩到兩次）：

- 第一版直接用查詢區間 → `scope='due'` 為了撈到所有逾期待辦會往回抓 10 年，超過 31 天上限，
  結果虛擬列**整個被跳過**，畫面上完全看不到日檢。
- 改成統一往回 14 天後 → 15 台 × 14 天 = **229 筆虛擬列洗版**，把真正該處理的逾期月保養埋掉。
- 定案：`scope='due'` 時**日檢只看今天、週檢只看本週**（前天沒做的日常點檢不會有人回頭補做）；
  其他 scope 才用完整視窗，且一律夾在 31 天內。實測預設視圖 56 筆、月檢視 343 筆。

### 回報與異動歷程

`已完成` 且（**月以上週期** 或 **判定 NG**）才寫一筆 `eq_history`（`action='保養'`、`user='system'`）。
日／週點檢每天 189 筆會把移轉／狀態變更這些真正重要的歷程洗掉（同 `_EQ_TRACKED_FIELDS`
刻意不追蹤備註的理由）。退回（`undo`）時會把那筆歷程一起刪掉——留著會變成
「歷程說做了、排程說沒做」的矛盾資料；只刪 `user='system'` 的，人工補登的不動。

`scope='due'` 的清單會濾掉舊的已完成資料，但**今天剛回報的一定留著**——
按了完成那列直接消失，會讓人以為沒存進去。

### 前端

左側選單「📁 保養管理 ▸ 🗓️ 保養排程」，選單項目上有到期徽章（逾期紅、只有本週到期時橘），
一進設備管理頁就會載入（`loadPlanStats()`），不用先切過去才看得到。

每列的操作：**✅ 一鍵完成**（判定 OK、今天、免填——九成情況就是這樣，不該逼人開表單）、
**📝 詳細回報**（NG／工時／執行人／備註）、**⏭ 跳過**；已回報的可 **↩ 退回**。
統計 chips 可點擊當狀態篩選。

# config.py（**兩份都要改**：根目錄那份才是執行時載入的）
MOBILE_ACCESS = True                            # 預設 False，打開才會綁 0.0.0.0

### QR

`static/vendor/qrcode.js`（qrcode-generator，MIT，56KB，無依賴）——**依硬規則下載到本地，
不用 CDN**。糾錯等級 `M`：標籤貼在機台上會沾油被刮，容錯高一點比較掃得動。
QR 內容是**完整網址** `http://<服務端>:5088/m/eq/<PDM編碼>`，手機相機原生掃了直接開頁，
不用裝任何 App。標籤頁把 `MOBILE_BASE_URL` 填進網址開頭，沒設定就用開這頁的 `location.origin`
（在服務端那台電腦上列印時最準）；**偵測到 localhost 會跳紅字警告**——那種標籤印出來手機掃了連不到。

### 手機版的設計取捨

- **不載 Bootstrap**：現場網路差，這頁只要開得快、按得到。CSS 全部內嵌。
- **按鈕做大**（`padding:.8rem`，三顆並排各佔 1/3）：現場戴手套、單手操作。
- **執行人存 `localStorage`**：每台設備都要重打姓名的話沒人會填。
- **NG 一定要寫狀況**，空的擋下來——「異常但沒寫哪裡異常」的記錄事後完全沒用。
- **拍照用 `<input capture="environment">`**：直接叫出後鏡頭，不用自己做相機介面。
  回報照片存 `EQUIPMENT_MAINT_PHOTO_ROOT`（`D.設備\保養回報照片\<設備編碼>\`），
  **刻意跟設備照片分開**——設備照片是「這台長什麼樣」，回報照片是「那天現場的狀況」，
  混在一起會把設備相簿灌爆（`scan_photos()` 也會把它們當設備照片收進 `eq_photo`）。
- 回報走的是跟電腦版**同一支** `plan/done`：虛擬列（日／週點檢）沒有 id 就帶
  `code+item_id+period_key`，後端這時才 lazy 寫進 `mt_plan`。
