> 何時要讀這份文件：修改 `templates/equipment_master.html`、`/api/equipment_master/*`、

## 二、資料正本的歸屬（重要決策）

**SQLite `equipment.db` 是正本，Excel 只是初次匯入來源。**

- 匯入後所有新增／修改一律在系統內做，**不要再回頭改 Excel**。
- 系統提供「匯出 Excel」按鈕，產生與現行格式相同的檔案，給不使用系統的同事看。
- 需要重新匯入時（例如有人偷改了 Excel）要當成**覆蓋**處理，並事先確認不會蓋掉系統內新增的設備。

### `source` 與 `origin` 是兩個不同的欄位，不可合併

| 欄位 | 意義 | 會不會變 |
|---|---|---|
| `source` | 這筆現在能不能被 Excel 覆蓋。**只要在系統內編輯過就變 `manual`**，重新匯入時會被略過 | 會變 |
| `origin` | 這筆當初打哪來的（`excel` / `manual`），只在 INSERT 時寫入 | **永不變更** |

**踩過的雷（2026-07-28 實測）**：原本只有 `source` 一個欄位，硬刪除的防護也拿它當門檻
（`if hard and source != 'manual'`）。結果只要使用者在系統內改過一次某台 Excel 設備，
它的 `source` 就變成 `manual`，於是**這台 Excel 設備就變成可以被真的刪掉**——測試時
確實把 `A01-101` 誤刪了（後來靠重跑匯入從 Excel 救回）。

因此 `/api/equipment_master/delete` 的硬刪除判斷**一定要看 `origin`**，不可看 `source`。
日後再加任何「這筆能不能刪／能不能改編碼」的權限判斷，也一律用 `origin`。

## 三、編碼規則

```
A 05 - 3 01
│  │    │  └─ 流水號   2 碼   同一屬性下第幾台
│  │    └──── 加工屬性 1 碼   規格差異（線軌/硬軌、走心/走刀、噸數…）
│  └───────── 機台類型 2 碼   立式銑床(BT40) / 車床-自動送料
└──────────── 群組分類 1 碼   A~I、M、O
```

`PDM編碼 = 群組 + 機台類型 + "-" + 加工屬性 + 流水號`

**群組一覽**（截至 2026-07 匯入時）

| 群組 | 名稱 | 台數 |
|---|---|---|
| A | CNC 車床／銑床類 | 43 |
| B | 鑽床 | 49 |
| C | 沖床 | 30 |
| D | 傳統銑床類 | 9 |
| E | 研磨類 | 13 |
| F | 測試機 | 5 |
| G | 包裝類 | 21 |
| H | 鉚釘機 | 3 |
| I | 表面處理 | 7 |
| M | 自動化 | 8 |
| O | 其它 | 1 |

合計 **189 台**、41 種機台類型。保管位置分布：加工 110、成品 54、詠設 24、生技 1。

**自動配號**：新增設備時選定 群組／類型／屬性 後，取該組合下現有最大流水號 +1。
不重用已刪除／報廢設備的號碼（報廢採軟刪除，`status` 改為報廢，編碼保留不放回）。

## 四、匯入時已知的資料問題

`build_equipment_index.py` 匯入時必須處理，並在設備清單上以紅標顯示 `needs_fix`：

| 問題 | 明細 | 處理方式 |
|---|---|---|
| 編碼格式錯誤 | `B-101`、`B-201`（傳統銑床，缺 2 碼機台類型） | **原樣匯入 + 標記待修正**，等使用者裁決要改 B07 還是併入 D 群組 |
| 屬性碼撞號 | B04 屬性 1 =「雙軸攻牙」也 =「窗型」；B04 屬性 2 =「開放式」也 =「銑滑座溝槽」 | 由上面 B-101/B-201 造成，修正後自解 |
| 屬性碼撞號 | B06 屬性 1 =「5/8自動鑽床」也 =「氣壓改伺服鑽床」 | 標記待修正（B06-103 建議改屬性 2） |
| 同名不同碼 | A03「硬軌-20m」用了屬性 1、2；C02「電控式-7.5噸」用了屬性 4、5 | 可能是刻意區分（不同床台／廠牌），僅提示不阻擋 |
| 舊編號重複 | `車06` → A05-105 與 A06-301；`B10` → E01-101~107 共 7 台 | 砂輪機共用可接受；`車06` 標記待確認 |
| 尾列空資料 | 最後一列只有「保管位置=加工」 | 略過（PDM編碼欄空白即跳過） |
| 規格塞在備註 | `1.床台1150mm/2.可裝油路刀把` | 依 `數字.` 切開寫進 `eq_spec` 鍵值表，原文保留在 `remark` |

PDM 編碼本身**無重複**。

**Excel 合併儲存格**：群組／類型／類型名／屬性／屬性名 都是縱向合併，讀取時必須「沿用上一個非空值」（forward fill），不能只讀當列。

### 編碼壞掉的設備不能查編碼字典（實作坑）

`B-101` 這種解析不出來的編碼，群組/類型/屬性碼是從 Excel 欄位硬推的（會推成 `B04-1`），
拿去 join `eq_type`/`eq_attr` 會查到**別台設備**的名稱（顯示成「專用機／雙軸攻牙」，
實際是「傳統銑床／窗型」）。因此：

- `equipment` 表另存 `type_name_raw` / `attr_name_raw`（Excel 原文）
- 查詢時 `needs_fix=1` 的設備一律顯示原文，不用字典：
  `CASE WHEN e.needs_fix=1 AND IFNULL(e.type_name_raw,'')<>'' THEN e.type_name_raw ELSE IFNULL(t.name,'') END`
- 匯入時也**不把** `needs_fix` 設備的類型/屬性名稱寫進字典，避免污染

## 五、資料庫設計（`equipment.db`）

不要動 `pdm_search.db`，另開一個庫。

```sql
eq_group   (code PK, name, sort)
eq_type    (group_code, code, name, sort, PRIMARY KEY(group_code, code))
eq_attr    (group_code, type_code, code, name,
            PRIMARY KEY(group_code, type_code, code))
equipment  (code PK,                       -- A03-501
            group_code, type_code, attr_code, seq,
            old_code, vendor, model, buy_date, remark, note,
            location,                      -- 加工/詠設/成品/生技
            status,                        -- 使用中/閒置/報廢/已售出
            needs_fix, fix_reason,
            created_at, updated_at)
eq_spec    (code, spec_name, spec_value, sort)   -- 床台/刀庫/行程/中心出水
eq_photo   (code, filename, is_cover, sort, uploaded_at)
eq_history (code, date, action, detail, user)    -- 移轉/報廢/售出/保養
```

**規格用鍵值表而非固定欄位**：CNC 要「床台／刀庫／行程／主軸／中心出水」，沖床要「噸數」，
包裝機要別的。每個群組配一套規格範本（欄位名清單），新增設備時自動帶出對應欄位。

Excel 的「設備移轉記錄」欄（如「2025/12/27從加工移去詠設」）匯入時解析成 `eq_history` 一筆。

頂層分頁「設備管理」`/equipment_master`，導覽列樣式照 `docs/nav-design.md`。
頁內採**左側選單版面**（`.page-layout` + `.page-sub-nav` + `.page-body`），
CSS 與互動比照管理頁（見 `docs/management-page.md`），子頁用 `switchSubPage(name)` 切換：

- 📁 **設備資料**：📋 設備清單、➕ 新增設備、🌳 編碼原則
- 📁 **歷程記錄**：🔧 維修記錄（見下方⑤）、📊 妥善率（見下方⑥）、🕒 異動歷程（跨設備瀏覽全部 `eq_history`，見下方④）

（2026-08-02：原本「編碼管理」是獨立的第三組，但底下只有編碼原則一個項目，
單項目的群組會讓側欄看起來比管理頁的側欄鬆散、不易掃視，所以併回設備資料組。）

### ① 設備清單（預設子頁）
- 搜尋語法同製令查詢：空格 = AND、`-` 前綴 = NOT；跨 編碼／舊編號／類型／屬性／廠商／備註／規格 全文搜
- 篩選列用**下拉選單**（群組／保管位置／狀態／編碼是否待修正），選項標題帶台數，
  有選值的選單加 `.on` 高亮；表格內徽章單擊＝設定對應選單的值、雙擊＝清空
  （即 `docs/badge-filter-convention.md` 的標準慣例）
- 表格照 `docs/table-design.md`，欄位：縮圖 · PDM編碼 · 類型 · 屬性 · 舊編號 · 廠商 · 型號 · 採購日 · 保管位置 · 照片數 · 技資
- 點列 → 右側滑出設備詳情：大圖輪播、規格表、異動歷程、技術資料檔案連結、「看稼動」按鈕（連 `/equipment`）
- **「🔒 快速編輯」解鎖後，廠商／型號／採購日可以在表格裡直接改**（`/api/equipment_master/inline_save`，
  2026-08-17 使用者要求，仿 `docs/oil-management.md` 油品清單那套做法）：工具列按鈕輸入密碼
  `maxclaw`（跟編碼鎖定、油品快速編輯同一組）→ 三欄變成可編輯，按鈕轉橘色提醒還開著；
  改完 Enter／點別處自動存檔，綠框閃一下＝存好了；點編輯欄不會順便把詳情抽屜打開。
  這只是防手滑，不是權限控制（密碼寫在前端 JS 裡）。
  **這三個欄位都在 `_EQ_TRACKED_FIELDS`**，所以會寫進異動歷程——但 `_eq_log_changes()`
  是拿完整的 after dict 跟 before 逐欄比對，只丟 `{field: value}` 進去的話，其餘追蹤欄位
  會被誤判成「改成空白」多記一筆假歷程；`inline_save` 因此要把 before 的其他欄位原封不動
  一起帶進去，只換掉正在編輯的那一個（實測：只改廠商，型號／舊編號／狀態都沒被誤動，
  當天歷程只有 1 筆）。採購日另外做前端格式檢查（`YYYY-MM-DD` 或 `YYYY-M-D`），
  contenteditable 沒有瀏覽器原生的日期格式驗證，打錯格式直接擋掉並還原成原值。

### ② 編碼原則
- 左側樹狀：群組 → 類型 → 屬性，每層顯示台數
- 右側列出該節點所有設備，並提示「下一個可用流水號」
- 可直接編輯類型／屬性名稱 = 編碼字典維護

### ③ 新增設備
- 三段下拉（群組／類型／屬性），每段皆可「＋新增」
- 選完即時顯示自動配號結果，並提示「此屬性下已有 N 台」
- 同頁多張照片上傳（拖拉）、規格依群組範本帶出欄位
- 存檔 → 寫 DB → 於網芳建立 `設備照片\<新編碼>\` 資料夾並存入照片

### ④ 異動歷程

跨設備瀏覽全部異動歷程（`GET /api/equipment_master/history/list`），不是某台設備詳情頁裡
的那份，是整個 `eq_history` 表。搜尋語法同其他清單（空格=AND、`-`=NOT，比對編碼/動作/
內容/群組名稱），篩選列是動作／來源／群組三個下拉選單（選項與台數由前端拿到全部資料後
自己算，沒有另開 stats API）。點列會直接呼叫既有的 `openDrawer(code, null)` 開啟該設備的
詳情抽屜（沿用抽屜裡既有的編輯/補歷程/刪除功能，這頁本身不重複做編輯 UI）。

「📤 匯出歷程到Excel」按鈕放在這個子頁的工具列（不是設備清單頁），呼叫
`/api/equipment_master/export_history`，見下方⑤。

### ⑤ 維修記錄（`GET /api/equipment_master/repair/list`）

**資料來源是採購登入表**（`config.PURCHASE_SHEET_ID` 那份 Google 試算表，跟管理頁
「採購登入表」子頁同一份），不是另外建的資料表——公司的維修花費本來就記在採購表裡。
沿用既有的 `fetch_google_sheet_csv` + `cache_get('purchase_list')` 快取，不另開連線。

**一定要用 `export?format=csv`，不可用 `gviz/tq?tqx=out:csv`**（`_fetch_purchase_rows_full`）

2026-07-29 踩到的大坑：**gviz 匯出會跟著試算表當下的「篩選狀態」走**。使用者在
Google Sheets 上開著篩選時，gviz 只回傳篩選後的 615 列；沒開篩選時回傳 12,213 列。
同一支程式在不同時間抓到的資料量天差地遠，而且**兩種情況抓到的維修筆數都是錯的**
（分別是 613 筆與 57 筆）。`export?format=csv` 端點永遠回傳完整原始資料
（16,958 列、維修 793 筆、95 家廠商），不受任何人的篩選操作影響。

發現方式：使用者看到畫面上維修廠商「只有榕鋒」覺得不合理，比對他螢幕上的實際
試算表才抓出來——當時抓到的 44 筆維修裡剛好幾乎全是榕鋒，數字自洽所以不易察覺。

**表頭不在第 0 列**：這份表第 0 列是篩選控制列（整列幾乎空白，只有 B 欄有「維修」
兩字），表頭在第 1 列。所以不能直接餵 `csv.DictReader`（會把空白列當表頭），
要用欄位位置 `_PUR_COL` 讀，並動態尋找「同時含日期與品名」的那列當表頭起點。

**篩選條件**（`_eq_repair_is_maintenance`）：`採購 其它` 欄 = `維修`，或會計科目含
「修繕」/「保養」。這兩欄都是人工填的，比拿關鍵字猜品名可靠。完整資料中有 793 筆符合。

**對應到設備**（`_eq_repair_match`）：
1. 先找「規格/品名/備註」裡的 `X##-###`，**且該編碼必須真的存在於 equipment 表**
2. 找不到才退而比對舊編號（例如「詠設.綜銑15」→ A03-502），長的先比避免「車1」誤命中
   「車15」；舊編號被多台共用時（砂輪機都叫 B10）無法判斷是哪台，寧可不猜

**編碼必須存在於設備主檔這點是關鍵**：採購表裡刀具料號長得跟設備編碼很像
（`SVF-A`**`B03-100`**`單斜固定鉗口`、`BT40-100-001鎖刀座` → `T40-100`），
單純用正則抓會把刀具誤判成設備。2026-07-29 實測若不做這層過濾，92 筆「疑似編碼」
裡有一半以上是刀具料號。

**已售出／報廢設備的維修不列出來**（2026-08-01 加）：機器已經不是我們的，那些維修是死歷史；
更重要的是清單上每一列都能填停機時數，而妥善率只採計 `status='使用中'` 的設備，
留著會讓人白填一堆永遠不會被計算的數字。實作方式是把這些編碼從 `codes`／`old_map` 拿掉，
對應不到設備的列本來就會被濾掉。實測 464 → 461 筆（移除的 3 筆都是已售出的 A05-102）。

**對應不到的不顯示**（使用者決定）：飲水機濾心、沖床共用件、氣壓虎鉗、2.5D投影機
這類歸不到某一台設備的一律排除。最終顯示 **464 筆、涵蓋 75 台設備、59 家廠商、
維修總額約 $3,371,488**（若看到的數字遠小於此，先懷疑是不是又走回 gviz 端點了）。

前端 `loadRepairList()`：篩選列是設備／群組／廠商三個下拉（設備選單順便顯示各台維修
次數），工具列即時顯示**篩選後**的維修總額；點列開啟該設備的詳情抽屜。

### ⑥ 妥善率（`GET /api/equipment_master/availability`）

```
妥善率 =（應有稼動時數 − 停機時數）/ 應有稼動時數
應有稼動時數 = 使用中台數 × 每日工時(預設8) × 工作天數
```

**使用者裁決的三件事（2026-08-01）**：

| 項目 | 決定 | 理由 |
|---|---|---|
| 工作天 | 以管理頁**行事曆**設定為準，沒設定的日子用週一～週五 | 見 `docs/calendar.md`；2026-08-02 起改由行事曆決定，國定假日／颱風假／補班都能自己調 |
| 台數 | 只算 `status='使用中'` | 已售出／報廢的機器本來就不該列入應有稼動 |
| 停機登記位置 | 在**維修記錄清單**每一列直接填 | 修什麼、花多少錢、停多久在同一列看得到 |
| 保管位置 | 預設只看**加工**，詠設不列入 | 見下方「不要用規格說明判斷詠設」 |

### 保管位置過濾：分子分母一起套用，且**不要用規格說明判斷**

`location` 參數同時決定分母的台數與納入計算的停機——詠設的機器不算我們的停機，
它們的產能自然也不該留在分母裡灌高妥善率。A 群組使用中 42 台＝加工 26、詠設 15、生技 1，
只看加工時分母是 26 台。

**使用者一開始的說法是「規格/說明有包含詠設的不要算」，但那個欄位靠不住**
（2026-08-01 實測 A 群組 355 筆維修）：

| 規格說明含「詠設」 | 設備保管位置 | 筆數 | |
|---|---|---|---|
| 沒寫 | 詠設 | 51 | ← 用文字篩會**漏掉** |
| 有寫 | 詠設 | 39 | |
| 有寫 | 加工 | 3 | ← 用文字篩會**誤殺** |
| 沒寫 | 加工 | 262 | |

還有 6 台機器同一台「有時標詠設、有時沒標」。那欄是採購人員手打的，
**一律以設備主檔的 `location` 欄為準**，不要回頭改用關鍵字比對規格說明。

分母為 0 時（月初剛好是週末、或該群組沒有使用中設備）前端會顯示原因，不是只寫「無資料」。

### 停機時數：`eq_downtime` 表與 `rep_key` 的選擇（重要）

採購登入表是**唯讀的 Google 試算表，寫不回去**，所以停機時數存在我們自己的
`equipment.db`，用 `rep_key` 對應回採購表的某一列：

```sql
eq_downtime (rep_key PK, code, date, hours, pur_seq, updated_at)
```

`rep_key` = `md5(日期|品名|規格|廠商|小計)[:16]`（`_eq_repair_key`）。

**為什麼不用採購表的序號欄**：序號雖然全表 16,964 筆唯一（實測），但只要有人在試算表
中間插一列，底下所有序號全部往下推，已登記的停機時數就會**整批對到別筆維修單**——
無聲的錯誤資料。內容雜湊碰到插列完全不受影響；最壞情況是有人事後改了品名／金額
導致該筆失聯（時數顯示不出來，看得出來也能補填）。**失敗模式要選看得見的那一種。**
`pur_seq` 仍冗餘存著，純粹當失聯時的人工救援線索。

實測（2026-08-01）795 筆維修候選資料用這個內容鍵無重複碰撞。

**踩過的雷**：`_purchase_date_key()` 回傳的是 `'YYYY-MM-DD'`（有連字號），期間篩選時
若寫成 `start.strftime('%Y%m%d')` 比較，會因為 `'0' > '-'` 而**永遠比不中**，停機時數
全部被濾掉、妥善率永遠 100%。兩邊字串格式必須一致。

`eq_downtime` 由 `_eq_ensure_downtime()` 在第一次用到時 `CREATE TABLE IF NOT EXISTS`，
**不需要重跑 `build_equipment_index.py`，也不要把 `equipment.db` 加進同步清單**
（見第十節）。

一鍵產生與現行 `PDM新格式編碼` 分頁同格式的 Excel（含合併儲存格），供不使用系統者參閱。

### 照片上傳（`/api/equipment_master/photo/upload`）

設備詳情頁「設備照片」旁的「📤 上傳照片」按鈕，可一次選多張。後端行為：

- **資料夾沿用既有的**：先查 `eq_photo` 這台設備現有照片用的是哪個資料夾（可能是
  `A05-303`，也可能是舊資料帶進來的 `A05-303同清`），沿用同一個，不會把同一台設備的
  照片拆進兩個資料夾。完全沒有照片時才新建一個**以編碼命名**的資料夾（例如 `A02-201`）。
- **檔名衝突自動改名**：撞到同名檔案時加時間戳記後綴，不覆蓋既有照片。
- **格式限制**：`.jpg/.jpeg/.png/.bmp/.gif/.webp`，其餘副檔名該筆略過（不中斷整批），
  回應會列出被略過的檔名。
- **封面**：這台設備原本沒有任何照片時，這批的第一張自動設為封面（`is_cover=1`）。
- **`claimed=1`**：跟人工認領的照片一樣標記，避免下次 `scan_photos()` 重新掃描時
  被覆蓋或搶走封面（但即使沒有這個標記，資料夾名稱本身就是編碼，重新掃描一樣認得出來，
  這個標記算是雙重保險，語意上也對——這確實是一次有意的使用者操作）。

前端 `uploadPhotos(code, fileList)`：成功後呼叫 `openDrawer()` 整個重畫詳情頁（因為
`dwBody` 是整段字串重建，上傳中顯示的訊息元素會被換掉，所以要在重畫完成後**重新抓一次**
`photoUploadMsg` 才顯示得出成功訊息），同時 `loadStats()`/`doSearch()` 讓清單表格的
「照片」欄位數字跟著更新。

**Ctrl+V 直接貼上**：在 `document` 上掛一個全域 `paste` 事件監聽（不是自己攔 `keydown`
判斷 `ctrlKey`——用瀏覽器原生 `paste` 事件，Windows/Mac 快捷鍵、右鍵貼上都會自然觸發，
不用另外處理跨平台差異）。只在「抽屜開著」且「剪貼簿裡有圖片類型」時才攔截並呼叫
`uploadPhotos()`，一般文字貼上（搜尋框、備註欄…）不受影響、也不會被誤攔。
測試技巧：`ClipboardEvent` 的 `clipboardData` 是唯讀屬性，用建構子塞不進假資料，
要測試時得用 `Object.defineProperty(event, 'clipboardData', {value: {...}})` 繞過去。

## 七、照片處理

**照片實體留在網芳**，不搬進程式資料夾——沒裝系統的人照樣能開資料夾看。

現況（匯入時）：13 個資料夾、81 張照片、27.3 MB，但**只有 4 個**是編碼命名

- 照片服務端點 `/api/equipment_master/photo?code=...&f=...`，路徑必須做防穿越檢查
  （參考 `build_cnc_program_index.py` 的安全修復做法）
- 寫入網芳前先確認資料夾可寫；共用資源的寫入務必先用本地副本驗證流程

### 異動歷程（eq_history）

三個來源，都寫在同一張表，用 `user` 欄位區分（詳情頁右側標「系統／人工／Excel」）：

| `user` | 來源 | 什麼時候寫入 |
|---|---|---|
| `system` | 系統自動 | 在系統內編輯設備，且**被追蹤的欄位**有變動時，一個欄位記一筆 |
| `user` | 人工補登 | 詳情頁「＋ 補一筆記錄」（保養／維修／移轉／狀態變更／其他） |
| `excel` | 匯入帶入 | Excel「設備移轉記錄」欄解析出來的舊資料 |

被追蹤的欄位定義在 `app.py` 的 `_EQ_TRACKED_FIELDS`：

| 欄位 | 動作標籤 |
|---|---|
| `location` 保管位置 | 移轉 |
| `status` 狀態 | 狀態變更 |
| `vendor` 廠商 | 資料修改 |
| `model` 型號 | 資料修改 |
| `old_code` 舊設備編號 | 資料修改 |
| `buy_date` 採購時間 | 資料修改 |

**刻意不追蹤備註／說明／規格**——那些是隨手修正的欄位，記進去只會把歷程洗版，
讓真正重要的移轉與狀態變更被埋掉。要新增追蹤欄位就往 `_EQ_TRACKED_FIELDS` 加。

實作要點：比對用的原值必須在 `UPDATE equipment` **之前**撈出來（`_eq_log_changes`），
順序寫反的話永遠比不出差異。另外「報廢」與「重新編碼」是在各自的程式分支另外寫入的。

歷程排序為 `date DESC, rowid DESC`（新的在上面，同一天以後寫入的排前面）。

### 人工補歷程：連動更新設備目前狀態

`+補一筆記錄` 表單（`/api/equipment_master/history/add`）不是單純寫一行文字，
選到會讓設備「現況」真的改變的動作時，會連動更新 `equipment` 表，
否則詳情頁上方顯示的目前狀態會跟歷程記錄兜不起來：

| 動作 | 連動欄位 | 前端額外欄位 |
|---|---|---|
| 移轉 | `location`（必填） | 保管位置下拉 |
| 轉賣／報廢／狀態變更 | `status`（必填） | 狀態下拉（選轉賣/報廐時預帶對應值） |
| 保養／維修／其他 | 無 | 純文字 |

寫入的 `detail` 是自動組字串（`保管位置：加工 → 詠設`）+ 使用者輸入的備註，兩者都空時退回動作名稱本身。

**編輯既有記錄則不連動**——`/api/equipment_master/history/edit` 只改文字內容
（日期／動作／備註），不會重新觸發設備狀態變更。這是刻意的：補改一筆舊記錄
不該把設備現在的保管位置/狀態改回過去的值。前端也因此在編輯模式隱藏保管位置／狀態選單。

**刪除限制在 `user='user'`**——只能刪人工補登的記錄，系統自動記錄（`system`）
與 Excel 帶入的（`excel`）是稽核軌跡，前後端都擋（前端隱藏刪除鈕、後端 400），
避免「狀態變更／移轉」的自動記錄被清空。編輯則沒有這個限制，系統記錄也能訂正文字。

`eq_history` 沒有另外定義 PK，直接用 SQLite 內建 `rowid` 當識別碼給編輯／刪除用，
省了一次 schema 遷移（安全前提：本專案不會對這張表做全表 `DELETE`+重建，只有
`build_equipment_index.py` 匯入時會 `DELETE WHERE user='excel'` 後局部重寫，rowid 穩定）。

### 異動歷程匯出成 Excel（`設備歷程.xlsx`）

清單頁工具列「📤 匯出歷程到Excel」按鈕，把全部設備的 `eq_history` 整份重建成獨立檔案
`config.EQUIPMENT_HISTORY_EXPORT_XLSX`（預設 `D.設備\設備歷程.xlsx`，跟 `設施設備編碼原則.xlsx`
同資料夾但**是不同檔案**）。

**這裡刻意不寫進 `設施設備編碼原則.xlsx`**——2026-07-29 用本地副本測試時發現該檔的
`PDM編碼` 欄是**公式**（`=$A$4&$B$4&"-"&D4&F4`），不是打死的文字。用 openpyxl
`load_workbook(path)`（預設 `data_only=False`）開檔、加一個分頁、`wb.save(path)`
存回去，openpyxl **不會重新計算公式**，存檔後公式文字還在，但公式算出來的**快取值**
會被整個洗掉——用 `data_only=True` 讀（包括我們自己的 `build_equipment_index.py`）
會看到 `PDM編碼` 欄全部變 `None`，要等有人用真的 Excel 打開這檔案存一次檔，
公式才會重新算出值。這是本地副本測試撈出來的問題（隔離測試可重現：單純
`load_workbook()` 再原封不動 `save()`，不加任何分頁，一樣會把快取值洗掉），
若沒先在本地測，會直接發生在共用正式檔上。

**因此改成獨立檔案**：每次匯出用 `openpyxl.Workbook()` 建一個全新的活頁簿
（不載入、不碰任何既有檔案），只有一張「設備歷程」分頁，整份重建（不是增量）。
寫入失敗（檔案被開啟中）時 fallback 存到桌面，訊息回報實際存檔位置——
沿用 `_save_batchcost_wb()` 的慣例（見 `docs/batch-cost.md`）。

**日後要在本專案寫入任何 Excel 檔案前，先確認該檔案是否有公式欄位**
（`cell.data_type == 'f'`，用 `data_only=False` 開檔才看得到），有公式的檔案
不能用「開檔→改→存檔」的方式寫入，除非改用不重算的獨立檔案，或改用會重新計算的
工具（例如控制真正的 Excel 應用程式）。

### 狀態選項

設備狀態（`equipment.status`）：使用中／閒置／**轉賣**／已售出／報廢（`轉賣` 為新增項目，
與 `已售出` 的差異由使用者自行認定，系統不做語意區分）。

### 自動配號規則

「下一個可用號碼」= 該範圍內**還沒被用掉的最小號碼**（不是最大號 +1），
但查的是全部設備、不篩狀態，所以**報廢設備的號碼不會被放回重用**，避免新舊設備同號。

尚未提供頁面上的「重新匯入」按鈕，要從 Excel 更新資料請執行
`python build_equipment_index.py --deploy`。

### 幫既有欄位加新欄位：`equipment.db` 不能靠 `CREATE TABLE IF NOT EXISTS`

`equipment.db` 是已經在跑的執行期資料庫（見下一節），舊資料庫檔案裡沒有新欄位，
`CREATE TABLE IF NOT EXISTS` 對已存在的表不會補欄位。2026-08-02 加「型號」
(`model`) 欄位時的做法：`_eq_conn()` 開連線時呼叫 `_eq_ensure_model_column()`，
用 `PRAGMA table_info(equipment)` 檢查欄位存不存在，不存在才 `ALTER TABLE ADD COLUMN`。
`PRAGMA table_info` 很便宜，每次開連線都檢查一次也沒差；等所有跑著的正式機都升級過
一輪之後這個檢查其實可以拿掉，但留著也無害。日後再加欄位比照這個模式，**不要**
只改 `build_equipment_index.py` 的 `CREATE TABLE`——那只對全新建立的資料庫有效，
對現有那份沒用。

## 十、`equipment.db` 是執行期資料庫，同步時要小心（2026-07-30 真實故障）

桌面應用執行中會直接寫入 `equipment.db`（照片上傳、設備編輯、補歷程都會寫進去），
**不是**單純的「隨原始碼一起部署」的靜態檔案。`sync_to_dist.py` 曾經把它跟 app.py
放在同一份無條件覆蓋清單裡：使用者在正式桌面應用貼上照片，寫進 dist 那份
`equipment.db`；之後任何一次同步（哪怕只是改 CSS）都會把開發機這份（沒有那筆照片）
蓋過去——**照片檔案還在網芳，但資料庫記錄整筆消失**，看起來像「上傳後不見了」。

現況：`sync_to_dist.py` 已移除這個檔案，只同步原始碼。要推送資料庫一律用
`python build_equipment_index.py --deploy`（明確、有意識的動作，不是同步的副作用）。

**救回遺失照片記錄**：照片實體檔案只要還在網芳就救得回來——重新跑一次
`build_equipment_index.py --deploy`，`scan_photos()` 會照資料夾名稱把它自動歸位
回資料庫（前提是資料夾名稱開頭是設備編碼）。欄位編輯（廠商/狀態/保管位置等）
一旦被覆蓋就真的救不回來，因為那些資料只活在資料庫裡，沒有網芳檔案當備份。

## 十一、`equipment.db` 改放網芳共用（2026-08-07）

原本 `equipment.db` 是本機檔案（開發機一份、`dist_embed/PDS系統/_app/` 一份，兩者不同步、
各自累積資料）。使用者要求多人在不同電腦同時使用設備管理，改成**兩邊 config.py 的
`EQUIPMENT_DB_PATH` 都指向同一個網芳路徑**：

```
\\192.168.1.99\加工部-資料夾\【技術資料】\D.設備\equipment.db
```

`app.py` 的 `EQ_DB_PATH = getattr(config, 'EQUIPMENT_DB_PATH', None) or <本機路徑>`，
沒設定這個 config 值時會退回舊的本機路徑（向下相容）。`build_equipment_index.py` 的
`DB_PATH` 也改用同一個邏輯，**`--deploy` 這個旗標保留但已經不會再做事**（不用複製到
`dist_embed`，因為現在就只有網芳這一份，開發機跟桌面版讀寫同一個檔案）。

**已知風險，刻意接受**：SQLite 官方文件明講直接放在網路檔案系統（尤其 Windows SMB
網芳）上，多人同時寫入時鎖檔機制不像本機硬碟可靠，理論上有機率造成資料庫損毀。
為了降低風險：

- `_eq_conn()` 開連線加了 `timeout=15`（原本沒設，預設是 0 秒——一撞到鎖就立刻丟
  `database is locked`）：遇到別人正在寫入時最多等 15 秒重試，而不是馬上失敗。
  實測驗證過：一個連線持有 `BEGIN IMMEDIATE` 鎖住寫入 4 秒，同時透過 API 呼叫
  `/api/equipment_master/save`，該次請求會等待鎖釋放後成功寫入（耗時約跟鎖持有時間
  相符），不會直接報錯。
- **刻意沒有開 WAL 模式**（`PRAGMA journal_mode=WAL`）：WAL 需要 shared memory
  mmap，Windows SMB 網芳對這個支援不穩定，反而更容易出問題；維持預設的 rollback
  journal（DELETE 模式）在網芳上相對安全。
- 仍應提醒使用者避免「多人同時對同一台設備編輯／同時上傳大量照片」這種高機率撞鎖
  的操作模式，尤其寫入量大、時間長的操作（例如一次上傳很多張照片）鎖住的時間也長，
  別人剛好在那個時間點存檔就可能要多等幾秒甚至偶爾逾時。

**遷移當下的操作記錄**：把 `dist_embed/PDS系統/_app/equipment.db`（185 台使用中＋
1 已售出＋2 轉賣＋1 閒置，共 189 台，桌面應用實際在用、資料最新的那份）整份複製到上面
的網芳路徑，作為新的正本。本機兩份舊檔案（開發機根目錄、`dist_embed/PDS系統/_app/`）
**保留但停用**，不會再被程式讀寫，純粹當作那個時間點的備援快照，之後也不會再更新。
