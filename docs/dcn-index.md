# 設計變更通知單索引（build_dcn_index.py）

> 何時需要讀這份文件：修改 `build_dcn_index.py` 或管理頁面「設計變更通知單」子頁時。

- 掃描 PDM Vault『00-研發部\02-文件資料\02-設計變更通知單』子資料夾，下載 xlsm 申請表。
- **PDM Card 變數值讀取自 Office 檔的 `docProps/custom.xml`**（Office Custom Properties），不是 worksheet cell——RR 新格式（2021+）的 cell 是空的，唯一可靠來源是 custom.xml。
- 讀取欄位：機型、提出人員、經辦、審核/核決、申請原因（PP_R_004_*_tasky 勾選項）、申請變更內容說明、工作流程狀態。
- 寫入 `pdm_search.db` 的 `dcn_index` 表。前端可點列開卡片彈窗、篩選提出人員、顯示已作廢/已結案。

## 增量更新（2026-07 改版，管理頁「⟳ 重新整理」按鈕預設用這個）

下載 xlsm + 解析 custom.xml 是整個流程最慢的部分（COM GetFileCopy 網路傳輸）。實測 1895 個
資料夾裡有九成以上狀態是「ECR結案／作廢／正式版本」等**終態**——一旦到了終態就不會再變，
沒必要每次重新整理都重新下載。所以預設行為改成三段式：

1. DB 裡沒有的資料夾（新申請單）→ 完整下載 + 解析（跟以前一樣）。
2. DB 裡已有、但狀態不是終態（`_TERMINAL_KEYWORDS` = 結案/作廢/正式版本/正式測試紀錄/歸檔）
   → 只呼叫 `f.CurrentState.Name` 讀目前工作流程狀態（不下載檔案），狀態有變才 UPDATE。
3. DB 裡已有、狀態已是終態 → 完全略過，連 COM 呼叫都不做。

`python build_dcn_index.py` 預設就是這個增量模式（不再 DROP TABLE）。要強制全量重建
（例如 schema 改了、資料看起來壞掉要重來）才加 `--full`。

`app.py` 的 `_run_dcn_reindex()` 解析 stdout 抓進度，改版後注意兩個正規表達式跟著變了：
- `找到 N 個子資料夾` → 總數（不變）
- `[idx/total]` → 逐筆進度（不變，三種分支都會印，所以略過的資料夾一樣會讓進度條快速往前跑）
- ~~`完成！寫入：N 筆`~~ → 改成 `索引共 N 筆`（現在印的是「新增/更新/跳過/錯誤」＋最終總筆數，
  不是單一「寫入」數字，改 app.py 進度解析要對應調整）
