# 製令製程明細表（SFCR06）

> 何時要讀這份文件：修改 `/api/sfcr06/list`（app.py）或管理頁「製程明細表(SFCR06)」子頁時。

## 背景

使用者想要的資料對應 ERP 原生畫面「製令製程明細表(SFCR06)」（鼎新/Computech ERP 內建報表，不是我們現有的 SSRS 自訂報表，SSRS 報表伺服器上查不到）。資料改成直連 `192.168.1.140` 的 `YC01` SQL Server（沿用 `get_erp_conn()`，跟 BOM/途程查詢同一套連線）。

## 資料表：SFCTA（製令途程交易檔）

`SFCTA` 是**製程層級**表（一個製令底下每個加工順序各一列），381 萬+ 列，欄位是 Computech 慣例的 `TA001`~`TA092` 無說明代碼。以下欄位是用使用者提供的真實 SFCR06 匯出資料逐欄比對驗證過的（不是猜測）：

| SFCTA 欄位 | 對應意義 | 驗證方式 |
|---|---|---|
| TA001 + TA002 | 製令單號（單別+序號） | `5166`+`20250217025` |
| TA003 | 加工順序 | `0010` |
| TA004 | 製程代號 | `J01` |
| TA005 | 性質（`1`=廠內製程／`2`=外包） | 外包列會對應到 TA007='鍾冶'/'遠利' 等廠商名 |
| TA006 | 線別/廠商代號 | `000-2` |
| TA007 | 線別/廠商名稱 | `成品部` |
| TA008 | 製程開工日（YYYYMMDD） | `20260127`→`2026/1/27` |
| TA009 | 製程完工日 | `20260204`→`2026/2/4` |
| TA010 | 投入數量 | `1375.000` |
| TA011 | 完成數量（只有該製程已完工才有值） | `1378.000` |
| TA022 | 標準人時（**單位是秒**） | `2750`秒 = `0:45:50`，跟報表欄位完全吻合 |
| TA023 | 標準機時（單位是秒，信心稍低但格式吻合） | `600`秒 = `0:10:00` |
| TA024 | 製程敘述/規格說明文字 | `1.T20圓刀螺絲 2.染黑 3.散裝` |
| TA030 | 實際開工日 | `20260127` |
| TA031 | 實際完工日（只有 TA032='Y' 才有值） | `20260202`→`2026/2/2` |
| TA032 | 完工碼（`Y`/`N`） | `Y` |

製程代號→製程名稱用 `LEFT JOIN CMSMW w ON RTRIM(w.MW001)=RTRIM(a.TA004)`（`MW002`=製程名稱），跟既有 `/routing` 產品途程查詢用的同一張代碼檔，不是另外新猜的。

## 產品品號/品名怎麼補

SFCTA 本身**沒有**品號/品名欄位。分兩段補：

1. 優先查既有的 `fetch_all_unfinished('all')`（製令查詢主頁同一套快取資料），用 `單別` 欄位（裡面其實放的是完整製令號，如 `5188-20260521009`）對應 `品號`/`品名`/`製令預計開工日`/`預計生產數`。
2. 上面查不到的（通常是已完工、不在「未完工」清單裡的舊製令），改查 `SFCTC`（移轉單明細）：`SELECT TOP 1 TC047, TC048 FROM SFCTC WHERE TC004=? AND TC005=?`（TC047=品號、TC048=品名，品名尾巴有 `||` 要去掉）。

第 2 段是逐筆查 ERP（N+1 query），日期範圍太寬時可能變慢，所以設了 500 筆上限（`missing_oids` 超過就不再補，那幾筆品號/品名留空）。實測：5 天範圍、373 筆需要 fallback 查詢，約 3.9 秒；同範圍若大多數訂單還在「未完工」清單命中第 1 段，可以快到 0.5 秒內。**日期範圍開太寬（例如整年）會明顯變慢，建議搭配關鍵字縮小範圍。**

### 關鍵字搜尋：有沒有日期區間，決定搜不搜得到品號/品名（2026-08-03 修正）

`keyword` 參數原本**只比對製令單號**（`TA001+'-'+TA002`），因為那是 SQL 階段唯一能篩的欄位——
品號/品名是上面這段邏輯事後才補上的，SQL 查 `SFCTA` 當下根本沒有這兩個欄位可比對。
實測使用者搜品號「FTB150」（其實命中的是品名）得到 0 筆，就是這個原因，不是 bug 是設計限制。

修法：`defer_keyword = bool(keyword) and bool(date_from or date_to)`——**只要同時有日期區間**，
就不在 SQL 階段篩關鍵字，改成先撈完整段日期範圍的資料、補完品號/品名後，
在 Python 端一次比對「製令單號 or 產品品號 or 產品品名」（不分大小寫）。
**沒有日期區間的純關鍵字搜尋（搜全部時間）維持舊行為**，只比對製令單號——這種情況
沒有日期範圍可以先縮小候選集合，若連品號/品名都要比對，等於要撈整張 `SFCTA`
（381 萬+ 列）逐筆補品號/品名，代價太高。

前端搜尋框的 placeholder／title 已更新為「製令單號/品號/品名關鍵字…」並註明這個限制。

## 預計完工日（製令層級，但限定查詢線別）算法

`SFCTA` 沒有「製令的整體預計完工日」這種單一欄位（只有逐製程的 TA009）。做法是同一個製令底下、**只看查詢的 `line`（例如加工課）自己的製程**，取這些列 `製程完工日`（TA009）的最大值，當作這張製令「在這條線」的預計完工日。

**這裡刻意不跨線別**：曾經一度改成「取全部線別（含外包/電鍍/成品部等）製程完工日的最大值」，理由是「整張製令送到最後一關才算完工」，但使用者回饋：**績效要看的是加工課自己的排定完工，不是整張製令送到最後一道外包/其他線別才算**——例如一張單加工課 5 月就做完了，但後面還要送外包電鍍到 6 月才整單結案，這種情況不該把加工課的延誤記錄算進 6 月的績效。所以改回**限定查詢線別自己**的最大值，不含其他線別/外包（2026-07-11 定案）。

若查詢時 `line` 留空（全部線別），沒有「哪條線自己」的概念可用，這種情況會退回最單純的做法：直接用每筆製程自己的 `製程完工日`（TA009）篩選日期區間，`預計完工日` 欄位留空。

## 月度負荷頁下半段：實際完工日口徑（2026-08-03 加）

「月度負荷」子頁上半段（`renderMloadTable`）是預計完工日、含未完工，回答「這個月*應該*要做多少活」；
下半段（`renderMloadActualTable`，同一支 `_achieveCache[selYear]` 資料，不必重查）改成逐製程自己的
**實際完工日**（`TA031`）、只算 `完工碼='Y'` 的，回答「這個月*實際*做完了多少活」，兩段口徑不同、
不要混用。歸屬邏輯跟「完工件數」子頁（`loadDoneCountData`/`renderDoneCountTable`）一致，只是那邊算件數、
這裡改算標準人時；也同樣濾掉實際完工日跨年（不屬於選定年度）的列。年度切換／月週切換兩段共用同一顆按鈕，
`loadMloadData()`／`mloadGranSwitch()` 都同時重畫兩段。

## 查詢區間依據：預計完工日（限定查詢線別），不是逐製程自己的製程完工日

`/api/sfcr06/list` 有指定 `line` 時，`date_from`/`date_to` 篩選的是**這條線自己的預計完工日**（上一節算法），不是逐製程自己的 `製程完工日`（TA009）。「製令製程明細表(SFCR06)」明細表、「加工達成率」、「月度負荷」三個前端子頁共用這支 API 且都固定傳 `line=加工課`，月份歸屬全部依 `預計完工日`（詳見各自的 `renderAchieveChart`/`renderMloadTable`，前端物件的 `r['預計完工日']` 欄位）。

**delay（延誤）判斷本身沒有變**：仍是逐筆比較該製程自己的 `製程完工日` vs `實際完工日`（`isDelayR`/`isDelaySfc`），只有「這筆記錄要算在哪個月」的依據換了。

### 為什麼要分兩步查

SFCTA 沒有製令層級欄位可以直接 `WHERE 預計完工日 BETWEEN ? AND ?`，只能分兩步（都限定 `RTRIM(TA007) = line`）：

1. **找候選製令號**：`SELECT DISTINCT TA001,TA002 FROM SFCTA WHERE TA007=line AND TA009 BETWEEN date_from AND date_to`。只要某張製令「這條線自己」的預計完工日落在區間內，達到最大值那筆製程的 TA009 本身必定也落在區間內，所以這一步不會漏單。
2. **撈候選製令「這條線自己」的全部製程**（同樣加 `TA007=line`，OR 分批查、每批 200 筆，同 SFCTC fallback 的作法）算出真正的預計完工日，篩掉候選中實際上落在區間外的單。因為候選查詢與完整撈取都已經限定同一條線，這一步撈出來的 `rows` 本身就是最終要回傳的資料，不需要再另外套用線別篩選。

### 已知代價與限制

- **`line` 留空（全部線別）時沒有「預計完工日」概念**：退回逐製程自己的 `製程完工日` 篩選，`預計完工日` 欄位留空；SFCR06 明細表的「全部線別」選項屬於這種情況，達成率/月度負荷不受影響（固定傳 `line=加工課`）。
- **全年查詢仍會比純製程完工日篩選慢**：兩步查詢（候選 + 分批撈取）跟直接 `WHERE TA009 BETWEEN` 比多了一次往返，但因為已經限定 `line`，資料量遠小於「不限線別」時的舊設計，效能可接受。`加工達成率`/`月度負荷` 兩頁預設抓全年，前端靠 `_achieveCache[year]` 做記憶體快取避免重複查。
- **跨年訂單行為**：如果加工課的製程排在今年 12 月，但同一張製令加工課還有一道製程排到明年 1 月，「今年」查詢只會抓到加工課排在今年的部分，這符合預期（因為現在只看加工課自己的完工日，不受其他線別影響）。

## 完工碼（TA032）大小寫不一致（2026-08-03 發現，已修正）

ERP 原始資料裡 `TA032` 不是乾淨的 `'Y'/'N'`——實測加工課製程紀錄：`'N'` 353 筆、`'Y'` 13,225 筆、
`'y'`（小寫）**3,199 筆，佔所有「已完工」紀錄的 19.5%**。前端十幾處判斷完工/延誤的地方
（`isDelayR`/`isDelaySfc`、加工達成率統計、完工件數子頁、月度負荷「實際完工工時」…）
全部是 `r['完工碼'] === 'Y'` 嚴格比對，在這次修正之前，這 19.5% 小寫 'y' 的紀錄會被
**誤判成未完工**，導致完工件數、實際完工工時、延誤統計全部systematically偏低。

**修法**：不逐一修改十幾處前端比對，而是在資料源頭 `/api/sfcr06/list` 組 `data` 時就把
`完工碼` 轉大寫（`(r[16] or '').upper()`），所有下游判斷不用改，直接吃到乾淨的 `'Y'/'N'`。
日後如果 ERP 又出現其他大小寫不一致的欄位（例如 `TA005` 性質碼），比照這個做法在後端統一
正規化一次，不要指望前端每個判斷點都記得做大小寫容錯。

發現經過：使用者問「5188-20260401047 這張單在 SFCR06 的完工日是什麼時候」，查出來
`實際完工日=2026/07/30` 但 `完工碼` 是小寫 `'y'`——若比對邏輯不做大小寫容錯，這張單
在「完工件數」「月度負荷實際完工工時」這些統計裡永遠不會被算進去，即使它明明已經完工。

## 已知限制

- 已完工很久的舊製令查不到「預計開工日」「預計產量」（因為這兩個欄位只從「未完工製令清單」補，舊製令早就不在那份清單裡了；`SFCTC` fallback 只補品號/品名，沒有補這兩個欄位）。
- `TA023`=標準機時的信心不如 TA022（標準人時）高，只用格式吻合來推論，沒有逐筆比對到第二筆驗證資料。
- 預設查詢範圍是當月（`製程完工日` TA009），避免一次掃過 381 萬列；前端日期欄位留空+有關鍵字時才會查全部時間範圍。
