# 判斷準則（把高階判斷變成可照做的 checklist）

> 讀者：本專案的任何 AI session。每條規則附一個本專案真實正例＋反例。寫於 2026-07-03。

## 1. 何時該升級模型（或由主對話親自接手）

**升級判準（滿足任一；此處指「主對話自己嘗試」的情況，subagent 的分層升級門檻另見
`dispatch.md` §4，兩者不同）：**
- 外部系統 API 的行為跟文件/記憶不符，且主對話已失敗 2 次
- 需要跨 3 個以上檔案同時推理因果（不是搜尋，是推理）
- 錯誤訊息看不出因果，需要設計實驗定位

✅ 正例：PDM 檔案簽入後掉進錯誤 workflow 狀態——查文件查不到分派時機，需要設計
「AddFile 後不簽入看狀態→寫 DB 變數→簽入→再看狀態」的實驗才能定位。這種值得高階模型做。
❌ 反例：`sed` 批次改 9 個 html 的顏色值失敗一次（跳脫字元寫錯）——修正跳脫字元重跑即可，
不用升級，這是機械錯誤不是判斷錯誤。

## 2. 何時算真的完成

**完成 = 以下全部打勾，缺一就不能回報完成：**
- [ ] `python -m py_compile` 通過（改了 .py 時）
- [ ] 同步到 dist_embed（`_app/` 下所有改過的檔；config.py 有改則**連根目錄那份**一起）
- [ ] 當天第一次完成任務時，`APP_VERSION` 已改為當日 `VYYYYMMDD`
- [ ] 回覆裡明講需要使用者做什麼（通常是「重啟程式再測」）
- [ ] 涉及外部系統寫入的：實際寫入路徑已驗證（不是只有程式碼寫完）

✅ 正例：修完 SFCR06 日期 bug → py_compile → 同步兩個 html → 告知重啟測試。
❌ 反例：治檢具申請單功能「寫完了」但 dist 根目錄 config.py 沒同步——使用者實測直接
AttributeError，一輪來回全浪費。**「程式碼寫完」不是完成，「使用者可測」才是。**

## 3. 何時停下來問使用者（其餘一律直接做）

**必問（滿足任一才問）：**
- 要對「非自己建立的正式共用資源」做第一次寫入（PDM vault、共用區 Excel、Google 試算表）
- 要刪除/覆蓋任何不是這個 session 建立的東西
- 要結束使用者可能正在使用的程序（先查證程序存在，再問）
- 兩個方案都合理但影響使用者日常操作習慣（例如把下拉選單換成按鈕組這種，如果沒被要求）

**不問直接做**：UI 措辭/配色/尺寸微調、加欄位、修 bug、重構、寫文件。
使用者的風格是截圖＋短指令快速迭代（見記憶 `feedback_terse_iterative_review`）——
照最合理解讀實作，做錯了下一輪截圖會糾正，來回成本遠低於停等。

✅ 正例：dist 版程式鎖住檔案無法同步 → 用 AskUserQuestion 問「我幫你關/你自己關」。
❌ 反例：「圖表下面不要有圓角」還去確認是哪個圖表——當下上下文只有一個有圓角的圖表，直接改。

## 4. 方向錯的訊號（該換路，不是加力重試）

**任一出現就停止當前路線：**
- 同一個症狀，換了 2 種修法都沒變化 → 你對根因的假設錯了，回頭重新定位
- 修 A 壞 B、修 B 壞 A 的蹺蹺板 → 抽象層選錯了，往上一層看
- 需要越來越多特例補丁才能讓方案成立 → 方案本身錯了

✅ 正例：治檢具索引看不到新申請單。第一直覺「索引沒重跑」重跑仍沒有 → 不是第三次重跑，
而是去讀索引工具的程式碼，發現它讀的是 Excel 儲存格而 API 建的單值在資料卡——根因完全在別處。
❌ 反例：openpyxl 開檔「卡死」，連殺三次重試三次——實際是 `import openpyxl` 被防毒掃描拖慢
30 秒。第二次卡就該用 `faulthandler.dump_traceback_later()` 看卡在哪，而不是重試。

## 5. 品質底線（回覆前的最後檢查）

- 對使用者的文字一律**繁體中文**；程式碼註解繁中；識別字英文
- 前端：字體規範（Noto Sans TC）、**禁 CDN**（第三方庫下載到 `static/vendor/`）、
  新表格套 `docs/table-design.md`、新徽章篩選套 `docs/badge-filter-convention.md`
- 回覆第一句就是結論（做了什麼/發現什麼），不要先鋪陳過程
- 不確定的事寫「未確認」，不要編造——特別是外部 API 行為、模型/參數名稱
- 動 management.html 前先讀 `docs/management-page.md`；動 PDM 前先讀 `docs/pdm-api-cookbook.md`

## 6. 補不了的事（誠實條款）

拆解＋驗證＋多樣本評審能補執行品質，補不了：**模糊需求的品味判斷**（例如「要有設計感」）。
遇到時的處理順序：(1) 找專案內已被使用者接受的同類先例照抄風格；(2) 沒有先例就做一版＋
說明取捨點等截圖回饋——單版投入超過原任務預期工作量的一半就先停下確認方向，不要越做越大；
(3) 連方向都拿不準才問。不要假裝有把握。
