# 給未來 session 的信

> 寫於 2026-07-03，Fable 5 的唯一一個 session 結束前。讀者是接手的你——大概率是 Sonnet。
> 別被「弱模型」這說法影響：這套制度存在的意義就是讓你不需要更強的模型也能把事做好。

## 一、三件使用者沒問、但我認為最重要的事

**1. dist_embed 是「部署產物」卻被當「第二源碼庫」在維護，這是最大的技術債。**
現在的流程是每改一個檔就手動 Copy-Item 過去，root config.py 還要另外記得——這個 session
就因此丟過一次功能失效。正確方向是：把「同步」收斂回 `sync_to_dist.py` 一個入口（讓它處理
鎖檔重試、root config.py、版本號檢查），或乾脆在完成大功能時用 `build_embed.py` 重打包。
哪天使用者抱怨「怎麼又是舊版行為」，先懷疑同步不完整，再懷疑程式碼。

**2. PDM 寫入功能有一個沒解決的組織依賴：使用者的帳號沒有刪除權限。**
建錯的資料夾/檔案自己清不掉（目前遺留物清單在 `docs/pdm-api-cookbook.md` 檔尾）。
在做任何新的 PDM 寫入功能前，值得提醒使用者跟 PDM 管理員談好一條「清理管道」，
或申請一個測試區資料夾。否則每次實驗失敗都在正式區留垃圾，遲早出事。

**3. 這位使用者是用「截圖＋短指令」高速迭代的人，你的回合價值取決於「一次改對率」。**
他不寫規格，他丟截圖。所以：改之前把截圖裡的每個細節看完（他圈的、他沒圈但明顯異常的）；
照最合理解讀直接做；回報短；錯了他馬上會再丟截圖。你最不該做的事是長篇確認和長篇解釋。
相關記憶：`feedback_terse_iterative_review`。

## 二、這套制度最可能的退化方式與預防

1. **索引失效**：新功能寫了卻沒進 CLAUDE.md 的延伸文件表 → 下個 session 找不到，重新踩坑。
   預防：每次新增 docs/ 檔案時順手加索引行（maintenance.md §1 已授權自由改）。
2. **踩雷記錄變垃圾場**：只加不刪，長到沒人讀。預防：maintenance.md §3 的精簡時機，
   看到就順手做，不要等「大掃除」。
3. **制度與現實脫節後被整包拋棄**：某條規則錯了（例如模型名稱變了），弱模型可能因此
   不信任整套文件。預防：maintenance.md §4——與現實矛盾時改文件而不是忽略文件。
4. **把「派 subagent」當教條**：在小任務上 spawn agent 反而更貴。dispatch.md §1 的
   「不派的情況」跟「要派的情況」同樣重要。
